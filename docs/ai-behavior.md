# AI behavior (Person 2)

## Request normalization

`normalize_request(text, now, timezone)` preserves the NormalizedRequest contract.
It calls the installed `google-genai` SDK server-side, using `GEMINI_API_KEY` from
the environment. The default primary is `gemini-3.5-flash-lite`; `GEMINI_MODEL` can override
it. Attempts use ten-second HTTP timeouts with SDK retries disabled, within a
shared 32-second scheduling budget (at most three models). No credentials or SDK error content are logged or
returned. The function does not load `.env` itself; application startup or the
caller supplies the environment.

Gemini receives the JSON Schema generated by Pydantic `Extraction` through
`response_json_schema` and JSON MIME type. This avoids the SDK legacy schema
encoding that Gemini rejected. Ambiguity uses a boolean field with a Python
validator requiring true, because the SDK rejects boolean Literal schemas. Python
independently validates the response JSON, forbids extra fields, rejects invalid
modes, duplicate specification names, negative/nonfinite/fractional-cent money,
naive timestamps, unconfirmed ambiguity flags, and reversed borrowing dates.
Internal specification lists are converted to the documented dictionaries. Buy
maps to `sale`; renting maps to `borrow`. The original text and source are assigned
by Python, never by Gemini.

Money is extracted as decimal USD dollar strings and converted with Decimal to
integer cents in Python. Purchase/rental budget and maximum refundable deposit
remain separate; neither is inferred from the other. Free is explicitly zero;
missing amounts remain null. Unknown specification values remain null, and no
known specifications produces an empty dictionary. Required compatibility (such
as jacket size) and preferred features (such as color unless mandatory) are separate.
Extraction semantics rely on Gemini and are proposals for user editing, not proof
that the model has correctly interpreted every phrase.

The prompt supplies current local time and the requested IANA timezone, including
America/New_York. Gemini is instructed to flag relative or ambiguous dates,
missing year/time, and DST ambiguity, with a proposed explicit timestamp when
possible. Python converts offset-aware timestamps to UTC with trailing Z and
adds a confirmation question for each ambiguity entry. Proposed dates require
user confirmation; Python does not independently detect all natural-language
ambiguity. Dates absent from the request must remain null.

Python adds follow-up questions for missing mode, category, budget and pickup
area; borrowing also asks for maximum deposit, start and return times. Other modes
ask for a needed-by deadline. Gemini can add item-specific compatibility questions,
such as trouser size for a suit. The request is explicitly treated as data, not
instructions to override extraction policy.

Missing credentials, timeout, SDK failure, malformed output or validation failure
returns `source="manual"`, null scalar constraints, empty specification dictionaries
and ambiguity list, the original text, and an instruction to fill the editable
fields manually. There is no guessed partial success.

## Deterministic listing matching

`match_listings(request, listings)` accepts NeedRequest owner-view dictionaries and
real listing dictionaries, returning the unchanged MatchEntry contract with
`source="deterministic"`. Owner-view fields override normalized fields, including
explicit nulls. No Gemini calls or input mutations occur. Titles/descriptions never
supply compatibility facts or instructions. Explanations reference structured fields
and provided IDs only.

Known category or required-specification mismatches, unsupported modes, unavailable
status/reservations, out-of-range dates, and prices exceeding budget are rejected.
String comparison trims outer whitespace and ignores case; it does not guess size
conversions, synonyms or missing attributes. Missing category or required specs go
to needs_confirmation with field names in unknown_required. Preferred differences
only affect ranking and shortcomings.

Sale uses sale_price_cents; borrowing uses rental_fee_cents. Null fees are unknown,
never assumed free. Explicit zero is accepted against a zero budget. An absent
budget imposes no price cap. Deposit is calculated separately as
`(proposed_item_value_cents * collateral_percent + 99) // 100`, rounding fractional
cents up so affordability is not understated. Unknown value/percentage needs
confirmation. Above max_deposit_cents yields needs_confirmation with the exact phrase
"deposit negotiation required" and unknown_required deposit_agreement, per the
current Person 2 assignment. It does not reject or automatically discount collateral.
A missing maximum imposes no deposit cap. Matching never supplies lender consent or
creates an agreement; lower-deposit acknowledgment still belongs to offer acceptance.

Offset-aware dates are compared as instants. Borrowing checks needed_by, use_start
and use_end against available_from/available_until; sale checks only needed_by.
Known boundaries are inclusive. Missing bounds for requested dates or malformed/
naive dates need confirmation; known conflicts reject. Invalid reversed intervals
reject. Availability notes do not establish date compatibility. When no dates are
requested, there is no date constraint. Pickup-window/area compatibility is not
ranked because this increment has no structured listing data mapping for it.

Each listing returns once, using the best supported requested mode: confirmed
before needs_confirmation before rejected. Within each bucket, fewer unresolved
fields rank first, then more matched preferences, then lower known sale/rental cost,
then mode and listing ID for deterministic ties. Score is matched preference count
plus `1 / (cost_cents + 1)` (zero cost component for unknown cost); rejected scores
are null. All buckets carry useful reasons, shortcomings and unknown_required.

Tests include the requested suit, size/category/mode failures, sale/rental budgets,
deposit negotiation, missing specs, dates/status, free loans and preference ranking,
plus cents rounding, nulls, offsets, alternative modes, prompt-like listing text,
input preservation and existing-route integration/access checks. Person 1's existing
normalize/matches stub tests need updating for source gemini/manual/deterministic
and fixture=false. The matching route already calls and hydrates the implementation;

## Bounded model fallback and live verification

Authenticated SDK model discovery listed generateContent support for
`gemini-3.5-flash-lite`, `gemini-3.5-flash` and `gemini-3.6-flash`. Each passed a
live response_json_schema probe returning {"ok": true}. These form the default
fallback order, in that order. An explicit GEMINI_MODEL goes first, followed by
these defaults, deduplicated (including the models/ prefix) and capped at three.
An explicit unsupported model is not silently replaced on a non-retryable error.

Only SDK APIError status 429 or 503 advances to another model. Authentication,
validation, malformed JSON, other HTTP errors and timeouts stop immediately and
preserve the manual fallback. All exhausted attempts also yield the same fallback.
There is no backoff or hidden SDK retry. Gemini rejected eight-second deadlines;
the supported ten-second minimum is used. No next attempt starts with less than
ten seconds left in the shared 32-second scheduling budget. Transport overhead
may add a small amount to the wall-clock time; this is not a process-level timer.
Successful extraction logs only the validated model identifier at INFO level via
server.intelligence.normalize. Neither request text nor credentials/errors are logged.
The public NormalizedRequest keys are unchanged.

## Reference-photo normalization (Person 1 endpoint handoff)

New exported function (implemented in server/intelligence/vision.py):

```python
def normalize_reference_image(
    image_bytes: bytes,
    mime_type: str,
    now: datetime,
    timezone: str,
    text: str | None = None,
) -> dict:
    ...
```

Input is one nonempty bytes object, a matching image/jpeg, image/png or image/webp
MIME type, timezone-aware current time, IANA timezone and optional user text.
Maximum input size is 5 MiB (5 * 1024 * 1024 bytes). JPEG/PNG/WebP magic signatures
are checked against MIME, not filenames. This is header validation, not a complete
image decoder; corrupt encoded images reaching Gemini produce the manual fallback.
No new imaging dependency was added.

Invalid uploads raise exported ReferenceImageError with safe message, code and
status: invalid_image/400 for empty/non-bytes input, unsupported_image/400 for
unsupported MIME or signature mismatch, payload_too_large/413 for oversized input.
These errors occur before any SDK call. Missing credentials/provider failure/invalid
structured output returns the existing editable manual NormalizedRequest; errors do
not leak credentials, image bytes or model response details.

Vision uses a strict Pydantic VisualAttributes schema with only broad category,
generic type, color, pattern and style. Extra fields (including size, exact model,
authenticity, condition, price, deposit, availability, location or ownership) are
rejected. The prompt prohibits deriving these from photos, text on labels or
embedded instructions. The actual visibility/semantic accuracy remains an editable
Gemini proposal, not a Python-verified fact. Unknown visual fields are omitted from
the specification map; unknown top-level scalar fields remain null. No visual
metadata is used as transaction evidence or a claim of ownership.

Optional text is extracted separately with the existing text schema, without the
image, so legitimate user-provided size, budget, deposit or dates can be retained.
Text constraints take priority over visual proposals. Newly added visual specs are
preferred unless conservative explicit text evidence marks that value as required
(e.g. "must be navy", "required color: navy", "navy is required"). More complex
wording can be edited by the user; it is not automatically promoted. Image-only
normalization never guesses buy/borrow mode or size.

A successful visual extraction returns the unchanged NormalizedRequest shape with
source gemini. Every identified visual attribute, including category, is listed in
an explicit confirmation question before search. An unclear image returns unknown
attributes and asks for a description or clearer photo. Original text is exactly
the supplied text, or empty string for image-only input. The photo is never persisted
or published by this function.

Vision and optional text share the existing three-model fallback approach and a
single 32-second scheduling budget. Each extraction tries at most three distinct
models; only 429/503 advance. HTTP deadlines are ten seconds with SDK retry disabled.
If optional text extraction fails after vision succeeds, the entire result is manual;
no misleading partial success is returned. Successful model logs contain identifiers
only. Text normalization and deterministic matching interfaces/behavior are preserved.
